# 4ViviTools Project Knowledge Base

Updated: 2026-07-13

This document is a detailed handoff of what is known about the project, the tools used, the local data paths, the training/build commands, and the current architecture decisions. It is meant for Vivi, Codex, Claude, or any future agent that needs to continue without rediscovering the whole project.

## 1. Product Summary

4ViviTools is a Ragnarok Online companion app built with Avalonia 11 and .NET 8. The main goals are:

- Read RO client state using OCR and vision.
- Detect monsters and entities accurately enough for Smart Bot targeting.
- Provide a beginner-friendly Smart Bot UI where the user selects RO hotbar keys, skills, buffs, pots, ammo, and emergency actions.
- Use driver-backed input paths where possible, with fallback input paths for compatibility.
- Support multiple RO clients attached to the tool.
- Provide optional Vision Assist GRF mode, where the game itself renders machine-readable monster markers so the tool does not have to guess from YOLO/OCR.

The project is Ragnarok-focused. Skill/item/monster names should be friendly in-game names, not script identifiers like `ac_double`, unless a low-level internal field explicitly needs the script id.

## 5. OCR Architecture

The app uses an out-of-process OCR worker:

```text
4rVivi.App -> 4rVivi.OcrServer over stdio
```

The OCR worker uses PP-OCR/PaddleOCR-derived ONNX models through RapidOcrNet. It can run CPU or CUDA depending on available native runtime/model setup.

Important OCR status strings seen in the app:


## 6. Capture Architecture

The project has used these capture modes:

- Client-window capture: hard attached to the RO window/client area.
- DXGI Desktop Duplication: monitor/screen capture path.
- PrintWindow/client-only capture: useful for hard-attached window reads.

User preference:

- Default should be client-window hard attach when reading one RO client.
- DXGI can be available for monitor capture, but the tool must not silently capture the wrong monitor when a client window is selected.
- Multi-client mode should capture each client window independently.

## 7. Entity Detection Architecture

There are two entity detection modes.

### 7.1 YOLO/OCR fallback mode

YOLO detects entity classes such as:

- monster
- player
- loot
- portal
- target
- target_hp
- player_hp

Entity model path:

```text
src\RapidOcrNet\models\yolo\entity.onnx
src\RapidOcrNet\models\yolo\entity_meta.json
```

The trained YOLO path is useful when the user does not use the Vision Assist GRF.

Known issues in YOLO-only mode:

- False positives in dark cave maps.
- Duplicate boxes on the same monster.
- Box flicker while character/screen moves.
- Name guessing can be wrong when multiple monsters share similar sprites.
- Confidence sliders must actually affect runtime filtering.

Mitigations implemented or planned:

- ByteTrackLite / LiveScene tracking.
- Min-hits before attackable.
- Max-age / LostGrace visual state.
- Map focus from `map_mobs.json`.
- Hard-negative mining.
- Roboflow + real screenshots + synthetic GRF scenes.
- Supervision QC sheets.

### 7.2 Vision Assist GRF mode

Vision Assist GRF is the preferred accuracy path when a server/client allows custom GRFs.

Instead of guessing monsters with YOLO, the GRF makes the game render:

- a pure red box around the monster,
- a machine-readable color code,
- a human-readable label using real mob names and combat hints.

Runtime then does a cheap color scan:

```text
screen frame -> red rectangle components -> color-code decode -> mobId/name -> SceneEntity
```

Important runtime files:

```text
src\4rVivi.App\Services\VisionAssistMarkerDetector.cs
src\4rVivi.App\Services\OcrService.cs
src\4rVivi.App\ViewModels\OcrReaderViewModel.cs
src\4rVivi.Core\Game\LiveScene.cs
src\4rVivi.Core\Game\ByteTrackLite.cs
```

Runtime contract:

- Red mask uses ratio test, not exact RGB:
  - `r >= 70`
  - `r - max(g,b) >= 35`
  - `r >= 2*g`
  - `r >= 2*b`
- Manifest provides marker constants:
  - `boxPx`
  - `codeCell` / `codeCellPx`
  - `codeCells`
  - `boxColor`
  - `mobs`
- Color-code is 3 cells, base-5, dominant-channel scheme.
- Runtime now uses 3x3 median sampling for code cells instead of one center pixel.
- If a red box is detected but the code does not decode, emit:
  - `MobId = -1`
  - `Name = "Monster"`
  - attackable fallback entity
- Logs should show:
  - `boxDet`
  - `codeReads`
  - `nameUnknown`
  - `targetSource=grf`
- If at least one GRF marker is found, YOLO is bypassed for that entity scan.

Known remaining runtime contract gaps:

- `MobId` is still lost after `VisionAssistMarker` becomes `OcrService.ScanFind`; ScanFind mainly carries `Value = name`.
- GRF entities still pass through LiveScene/ByteTrackLite. They are preconfirmed, but this is not literally "no tracker in GRF mode."
- A stricter GRF-direct path could bypass tracker completely or preserve source/mobId downstream.

Important builder design:

- Writes standard `Master of Magic` GRF header.
- Writes to `.tmp` then atomically replaces output.
- Verifies written GRF header/table before success.
- Supports CP949/EUC-KR/CP1252 internal GRF names.
- Caches GRF file tables to avoid re-reading the 100 MB source GRF for every monster.
- Can build `mobid_sprite_map.json` from RO Lua/Lub files.
- Manifest uses real display names from `gamedata.json`, not sprite filenames.
- Refuses output if too many scoped mobs fail.

Claude final design implemented in Python:

- Leave body frames untouched.
- Add one indexed marker frame to the SPR.
- Add one ACT layer per frame pointing at the marker frame.
- Use `_act_body_offset` to place marker at the largest body layer, not a side accessory.
- Support mixed indexed/truecolor sprites using `spr_split` and `spr_emit`.
- Copy truecolor frame bytes raw so color order issues do not corrupt body colors.
- In `--library` mode, write baked sprites to:

```text
data\sprite\visionassistant\
```

and leave the live monster folder empty until the picker promotes selected mobs.

Recent safety patch:

- Marker palette slots now avoid indices used by original indexed body frames. This preserves original body colors.

Known builder coverage:

- A previous direct all-scope run produced:
  - baked: 2309
  - skipped: 281
  - output: `VisionAssist.grf`
- The Claude-style library run produced:
  - `VisionAssistLibrary.grf`
  - manifest with about 2300 entries
- Source `ViviMobsBoxMasterofMagic.grf` is incomplete for some newer mobs. For full coverage, add a clean real client `data.grf` as a second `--source-grf`.

## 13. Smart Bot Architecture

Important files:

```text
src\4rVivi.Core\Automation\SmartBotEngine.cs
src\4rVivi.App\ViewModels\SmartBotViewModel.cs
src\4rVivi.App\Views\SmartBotView.axaml
src\4rVivi.Core\Automation\SmartBotTrainingTuning.cs
src\4rVivi.App\Services\SmartBotTrainingRecorder.cs
```

Desired behavior:

- User picks RO keyboard hotbar keys in one friendly grid/card system.
- User does not manually assign controller buttons.
- Tool assigns non-conflicting controller buttons internally when virtual controller mode is enabled.
- If the same controller button would be used for two things, the UI should prevent or clearly warn.
- Start and Stop buttons/hotkeys should be separate and reliable.
- Panic/Stop should always work.

Attack behavior:

- When a monster is attackable, attack immediately.
- Normal attack: left-click monster.
- Skill attack: press selected skill key, then click monster.
- If SP is too low for the skill, fall back to normal click.
- If stuck/cannot attack after configured or auto-calculated delay, use teleport key.
- If no specific monsters are selected, attack all monsters.
- If monster filters are selected, attack only those.
- Monster death is detected by disappearance or HP bar reaching zero.

Timing behavior:

- Default timing values should use automatic formulas.
- Manual override is allowed with numeric values.
- `-1` means auto formula.
- Hide complicated values from newbies where possible.
- Keep key delay/walk delay/skill delay/teleport delay available for advanced users.

Training behavior requested:

- Smart Bot Training button records user behavior:
  - keystrokes,
  - timings,
  - attacks,
  - teleport behavior,
  - potion behavior,
  - kill time per monster,
  - skill usage patterns.
- Then it computes averages/best values and updates formulas in real time.

## 22. Notes For Future Agents

- Do not assume YOLO is the best path if Vision Assist GRF is enabled. GRF mode should be primary.
- Do not silently revert user changes; this repo is very dirty and many files are intentionally modified.
- Use `rg` first for searching.
- Use `apply_patch` for manual edits.
- Be careful with Korean sprite paths and Windows console encoding.
- For PowerShell, do not use bash heredoc syntax like `python - <<'PY'`.
- The user prefers no zip unless explicitly requested.
- The user wants release builds, not only source changes.
- Keep UI beginner-friendly: hide advanced formulas where possible, show `-1 = Auto` clearly, and avoid forcing users to understand OCR internals.
